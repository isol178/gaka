# Gaka コンセプトシート

**Gaka**（画架）: 絵を描くエージェントのためのハーネス

名前の由来は画架（イーゼル）。絵を支える台であり、読みは「画家」にも重なる。

## 1. 一言で

LLM が「描く → 見る → 直す」を繰り返して絵を仕上げるための専用ハーネス。絵画から始め、イラストやポスターにも使えるようにする。画像トークンを節約しながら、少ない反復で質を上げることを目指す。オープンな技術だけで組み、特定のモデルやベンダーに依存しない。

## 2. 背景と課題

- LLM は座標を一発で決める SVG 直書きが苦手だが、手続き的な描画（ループ、ノイズ、重ね塗り）なら精細な絵を作れる。
- 質を上げるには描いた結果を見て直す反復が要るが、画像入力はトークン効率が悪い。
- 汎用のコーディングエージェントで描かせると、毎回フル画像を見る、コード全体を書き直す、自己評価が甘い、といった無駄が出る。
- 絵の中の文字は崩れやすく、ポスターのような用途では致命的になる。
- 特定モデルの機能に寄せて作ると、モデルを替えたときに動かなくなり、比較もできない。

## 3. コンセプト

**「画家のアトリエ」をハーネスとして再現する。**

| 画家の行動 | ハーネスでの対応 |
|---|---|
| 離れて全体を見る | 低解像度サムネイルで構図・配色を確認 |
| 近づいて細部を見る | 指定領域だけを高解像度でクロップ |
| 下地から順に描く | レイヤー単位の制作と状態管理 |
| 筆を選ぶ | 筆致 DSL（高水準の描画命令） |
| 活字を組む | 同梱フォントによる文字組み |
| 師匠に講評をもらう | 別モデルの Critic による評価 |

## 4. 対象範囲

| 対象 | 主に使う要素 | 段階 |
|---|---|---|
| 絵画 | 筆致の重ね塗り、質感 | MVP |
| イラスト | 塗り面、輪郭線、筆致 | 第2段階 |
| ポスター | 上記＋文字組み、レイアウト | 第2段階 |

## 5. 設計原則

1. **資産は DSL に置く**: 絵の実体は JSON の筆致 DSL とする。言語やレンダラーは後から差し替えられる。
2. **オープンな標準だけを使う**: Web 標準の Canvas 2D、JSON、JSON Schema、PNG、オープンライセンスのフォント。独自形式や特定ベンダーのサービスを前提にしない。
3. **モデルを選ばない**: モデルに求めるのは「テキストを読み、JSON を返す」ことだけにする。それ以外の能力は任意とし、あれば活かす。
4. **決定的に再現できる**: 同じ DSL とシードからは、いつでも同じ絵が出る。
5. **文字は描かせず、組ませる**: モデルは文字列と配置を指定するだけで、字形はフォントが担う。

## 6. 技術選定

| 役割 | 採用 | 理由 |
|---|---|---|
| 基準レンダラー | JavaScript + Canvas 2D | Web 標準で、ブラウザがあればどこでも動く。HTML 1枚で作品を配れる |
| ハーネス内の描画 | ヘッドレスブラウザまたは node-canvas | 基準レンダラーと同じコードを使える |
| 観察と数値指標 | Python（NumPy、Pillow） | 画像解析の道具が揃っている |
| DSL の形式 | JSON + JSON Schema | どの言語・どのモデルでも扱え、機械的に検証できる |
| フォント | オープンライセンスのフォントファイルを同梱 | OS に入っているフォントに左右されず、再配布もできる |

注意点と対策

- JavaScript の `Math.random` はシードを指定できない。自前の疑似乱数生成器を持ち、シードを DSL に記録する。
- 描画結果はブラウザや描画ライブラリの実装で微妙に変わる。評価時はレンダラーとそのバージョンを1つに固定する。

採用しなかった候補

- **シェーダー（WebGL、WebGPU）**: 筆跡を重ねる描き方に向かず、モデルがデバッグしにくい。
- **SVG**: 数万ストロークを置くとファイルが肥大する。
- **Python 単独**: 見る人の環境でそのまま動かせない。

## 7. モデル非依存の設計

### 7.1 モデルとの接点を最小にする

- 入出力は「テキスト（＋任意で画像）を渡し、JSON を受け取る」だけに絞る。ベンダー固有のツール呼び出しや構造化出力の機能には頼らない。
- 返ってきた JSON はハーネス側で JSON Schema により検証する。不正なら、エラー内容を添えて再試行させる。
- 修正は差分パッチではなく **レイヤー単位の全置換** とする。パッチ形式はモデルによって精度の差が大きいため。
- プロンプトは平易な指示と DSL の仕様、少数の例で構成する。特定モデル向けの書き方は使わない。

### 7.2 能力プロファイル

モデルごとに次の項目を設定ファイルで宣言し、ハーネスが振る舞いを切り替える。

| 項目 | 使い道 |
|---|---|
| 画像入力の可否 | 不可なら数値と文章による描写だけで反復する |
| 画像1枚あたりのトークン消費 | 観察の予算配分に使う |
| コンテキスト長 | 履歴をどこまで渡すかを決める |
| 入出力の単価 | コスト集計に使う |

### 7.3 役割ごとにモデルを割り当てる

- Planner、Painter、Critic には、それぞれ別のモデルを設定できる。
- 画像を見られないモデルを Painter に使う場合は、画像を見られるモデルを Critic や描写役に充てて補える。
- 接続部分はアダプターとして分離し、商用 API でもローカルで動かすオープンウェイトのモデルでも同じように扱う。

### 7.4 副産物としてのベンチマーク

同じお題・同じ予算で複数のモデルに描かせれば、モデルごとの「描く力」と「見て直す力」を比べる評価基盤になる。

## 8. アーキテクチャ

```
[Brief] → Planner ─→ Painter ─→ Validator ─→ Renderer ─→ Observer ─→ Critic
              ↑                     │                                   │
              │                再試行（不正な JSON）                     │
              └──────────────────── 修正指示 ←──────────────────────────┘
```

- **Planner**: お題から構図・パレット・レイヤー構成・完成条件を決める。
- **Painter**: 1回の反復で1レイヤーの DSL だけを書き直す。
- **Validator**: DSL を JSON Schema で検証する。
- **Renderer**: DSL を Canvas 2D で決定的に描画する。
- **Observer**: Critic に渡す材料を作る。画像はなるべく渡さず、数値とクロップで済ませる。
- **Critic**: 講評し、次に直す箇所を1〜3点に絞って返す。

モデルを呼ぶのは Planner、Painter、Critic の3つだけ。残りは通常のプログラムとする。

## 9. 文字組み

- モデルが指定するのは、文字列・フォント・サイズ・色・配置枠・揃え方だけ。字形は一切描かせない。
- フォントはファイルとして同梱し、レンダラーが明示的に読み込む。OS のフォントは参照しない。
- 配布用の HTML にはフォントを埋め込み、1ファイルで同じ見た目を再現する。
- 改行と禁則処理はハーネス側で行う。モデルに行の折り返し位置を計算させない。
- 文字の問題は数値で検出して返す。画像を見せずに直せる。
  - 配置枠からのはみ出し
  - 文字同士や主題との重なり
  - 文字色と背景色のコントラスト比

## 10. 観察戦略（トークン節約の要）

1. **数値フィードバックを優先**: 色ヒストグラム、明度分布、彩度、エッジ密度、文字のレイアウト検査などをテキストで返す。画像は使わない。
2. **サムネイル**: 構図・配色の判断には 256px 程度の画像を使う。
3. **差分クロップ**: 前回から変わった領域だけを切り出して見せる。
4. **注視クロップ**: Critic が要求した領域だけを高解像度で見せる。
5. **フル画像**: 節目と最終確認だけに使う。

反復ごとに **画像トークン予算** を設け、Observer が能力プロファイルを見て、その範囲内で見せ方を選ぶ。画像を見られないモデルでは 1 だけで反復する。

## 11. 状態表現

- **レイヤー構造**: 背景 / 中景 / 主題 / 光と影 / 仕上げ / 文字。各レイヤーは独立した命令列とする。
- **筆致 DSL（例）**

```json
{
  "canvas": { "width": 1024, "height": 768, "seed": 42 },
  "fonts": {
    "title": { "file": "fonts/title-font.woff2" }
  },
  "regions": {
    "sky": { "x": 0, "y": 0, "w": 1, "h": 0.55 },
    "titleBox": { "x": 0.08, "y": 0.72, "w": 0.84, "h": 0.2 }
  },
  "layers": [
    {
      "id": "background",
      "ops": [
        {
          "op": "stroke", "region": "sky", "dir": "horizontal",
          "length": "short", "density": "high",
          "palette": ["#9db7d5", "#c9d8e8"],
          "jitter": 0.15, "opacity": 0.4
        },
        { "op": "glaze", "region": "sky", "color": "#f2c48d", "opacity": 0.1 },
        { "op": "noise", "scale": 0.02, "strength": 0.05 }
      ]
    },
    {
      "id": "text",
      "ops": [
        {
          "op": "text", "region": "titleBox", "font": "title",
          "content": "山の朝", "size": 0.09,
          "color": "#1f2a37", "align": "center"
        }
      ]
    }
  ]
}
```

- 座標とサイズは 0〜1 の比率で表し、解像度に依存させない。
- 生の JavaScript を書かせる拡張は標準では無効とする。使う場合はサンドボックス内で実行する。
- 全反復の DSL・画像・講評を履歴として保存し、いつでも巻き戻せるようにする。

## 12. 評価

- **品質**: 人間による一対比較（Elo）、Critic スコア、お題との類似度スコア。
- **効率**: 完成までの総トークン数（画像 / テキスト別）、反復回数、所要時間、コスト。
- **頑健性**: 不正な JSON の発生率と再試行回数。
- **文字**: レイアウト検査の合格率、指定した文字列が正しく読めるか。
- **主要な問い**
  - 何回見て直せば質が頭打ちになるか。
  - 観察戦略によって「質とトークンの関係」はどう変わるか。
  - その傾向はモデルが変わっても成り立つか。

## 13. MVP スコープ

- お題: 風景画（空・山・水面）に限定する。
- レイヤー3枚、DSL 命令は stroke / fill / glaze / noise の4種。
- 比較する観察条件
  - A: 毎回フル画像を見る（ベースライン）
  - B: サムネイル＋数値
  - C: B＋差分・注視クロップ
- モデルは性格の違う3種で試す: 大型の商用モデル、小型の商用モデル、ローカルで動くオープンウェイトのモデル。
- 各組み合わせで同じお題を描かせ、品質とトークン消費を比較する。

第2段階: text 命令とレイアウト検査を加え、題字入りのポスターを描かせる。

## 14. リスクと論点

- 数値指標は「絵として良いか」と必ずしも一致しない。Critic が指標に過適合するおそれがある。
- DSL を絞りすぎると表現の幅が狭まる。逆に広げすぎると、小さいモデルが正しく書けなくなる。
- 最小限の能力に合わせると、高性能なモデルの力を活かしきれない。能力プロファイルでどこまで吸収できるかが論点になる。
- Critic と Painter が同じモデルだと評価が甘くなる。モデルを分けるか、評価基準を明文化して対策する。
- 日本語フォントはファイルが大きい。配布時は使う文字だけに絞り込む（サブセット化）必要がある。
- 縦書きは Canvas 2D の対応が弱い。ハーネス側で1文字ずつ配置する実装が要る。
- フォントのライセンスは、埋め込みと再配布が認められているものに限る。
- 既存の作品や画風の模倣に寄らないよう、お題とスタイル指定にガードを入れる。

## 15. 発展案

- 講評の履歴から「効いた修正パターン」を抽出し、再利用できる知識として蓄える。
- 人間が途中で領域を指さして指示できるインタラクティブモード。
- 別言語のレンダラー（Python、Rust など）を追加し、同じ DSL から同じ絵が出ることを確かめる。
- 印刷向けの高解像度出力と PDF 書き出し。
- アニメーション（フレーム間の一貫性管理）への拡張。
